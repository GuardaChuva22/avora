# Avora — Decisões

Registro das decisões tomadas pelo proprietário. Uma decisão nova recebe o próximo número; uma decisão revista é marcada como substituída, nunca apagada.

## Tomadas em 2026-11-10

| # | Decisão | Motivo |
|---|---|---|
| D01 | Avora é **pessoal e privado**, um único operador, sem distribuição, billing ou multi-tenant. | É uma ferramenta pra uma pessoa só. |
| D02 | A spec de 305 requisitos obrigatórios foi **substituída** por 12 módulos concretos ([spec.md](spec.md)). Os arquivos antigos ficam em `docs/archive/` como referência. | A lista era um inventário do mercado, não um projeto, e o "tudo obrigatório" impedia chegar a algo usável. |
| D03 | **Orquestrar, não reinventar:** Claude Code e Codex são os motores pesados; o Avora coordena. Um motor nativo leve cuida de tarefas simples e do heartbeat. | Esses motores já são de ponta; recriá-los custaria meses pra ficar pior. |
| D04 | **Prioridades:** proatividade e autonomia em primeiro lugar, depois roteamento e auditoria. | Valor declarado do proprietário. |
| D05 | O Avora deve ser um **funcionário 24h com iniciativa**, não um feed de notícias: conecta, antecipa, executa e evolui. Base concreta: funcionalidades de Grok Bot, OpenBot, Hermes e OpenClaw adaptadas. | "Se for só notícia e promoção, grupo de Telegram faz de graça." |
| D06 | **Omniarch é a fonte da verdade da vida pessoal** (tarefas, metas, agenda, finanças, notas, gostos). O Avora lê e escreve lá pela API, nunca em arquivos soltos. | Os dados ficam visíveis e editáveis numa interface que o proprietário já usa. |
| D07 | O Avora tem **app próprio** (desktop Windows e Android) com chat próprio. O **chat do Omniarch será removido**. | Mais organizado: Omniarch guarda, Avora conversa e age. WhatsApp foi descartado por ser burocrático. |
| D08 | **Núcleo em Go.** Rust foi avaliado e descartado; TypeScript também. | Go é leve (~10–30 MB de RAM), gera binário único e é fácil de desenvolver com IA. Rust economizaria ~15 MB (menos de 2% do uso real) com desenvolvimento bem mais lento. A velocidade da linguagem não importa: >99% do tempo é espera pelo modelo. |
| D09 | **Infraestrutura atual: só a VPS de 6 GB + o PC Windows.** A VPS de 512 MB fica de fora por enquanto (candidata futura a vigia e backup). | Simplicidade. |
| D10 | Rede só pelo **Tailscale**, nenhuma porta pública. | Mesmo modelo que já funciona no Omniarch. |
| D11 | No máximo **3 agentes pesados simultâneos** na VPS; o resto vai pra fila. Trabalho pesado vai pro PC quando ele estiver ligado. | Orçamento de RAM: ~4,5 GB livres; cada sessão de Claude Code/Codex usa ~200–500 MB. |
| D12 | **Níveis de autonomia** por categoria de ação (0 sugere, 1 faz e conta, 2 faz em silêncio, 🔒 sempre aprova). | Autonomia alta sem perder controle. |
| D13 | O Avora roda numa VPS (a mesma de outro projeto do dono) como usuário `avora`, database `avora` própria, publicado no tailnet na porta **8443**. | Isolado dos outros serviços da mesma máquina, reaproveitando Postgres e Tailscale que já existem. |
| D14 | O **motor nativo** começa no **NVIDIA build** com `deepseek-ai/deepseek-v4.1-flash`, via API compatível com OpenAI (troca de provedor só por variável de ambiente). A chave fica só em `/etc/avora/avora.env`, gravada por entrada oculta. | Chave que o proprietário já tem, sem custo. Trial: ~40 req/min e os termos podem permitir uso dos prompts, então dados sensíveis do Omniarch não vão pra lá sem decisão consciente. |
| D15 | Modelo padrão do motor nativo trocado para **`nvidia/nemotron-3-ultra-550b-a55b`**; alternativa rápida: `minimaxai/minimax-m3.1-flash`. | Teste em 2026-11-10 a partir da VPS: Nemotron 3 Ultra escreveu a 1ª palavra em 1,6 s (MiniMax 4,9 s, Nemotron 3.5 Lightning 8,5 s, Mistral Large 4 38,6 s, GLM 5.3 151 s, gpt-oss-20b 128 s); o DeepSeek V4.1 Flash ficou na fila mais de 200 s, e passou de 240 s no teste. |
| D17 | **Claude Code e Codex são ferramentas, nunca o motor de um agente.** Todo funcionário pensa com o motor nativo e age por ferramentas: delega ao Claude Code ou ao Codex, cria e altera rotinas e responsabilidades, consulta colegas. O app é **chat-first**: o dono conversa e os agentes configuram tudo; painéis e formulários são o caminho secundário. Substitui a parte "motor por agente" de D03 e do M8. | Decisão do proprietário em 2026-11-10: escolher motor, modelo e permissão por agente e configurar rotinas em modais distorcia a ideia original de facilidade e simplicidade. |
| D16 | **Apps nativos:** desktop Windows em **C++20 + Qt 6/QML**; Android em **Kotlin + Jetpack Compose** (APK direto, sem Play Store). O app web em React feito antes desta decisão é provisório e sai quando o desktop Qt o substituir. | Retoma AV-007 e AV-008, preferência explícita do proprietário. Os apps só falam com a API do `avora-server`, então o núcleo em Go não muda. |

## Tomadas em 2026-11-11

| # | Decisão | Motivo |
|---|---|---|
| D18 | **Plugins: ler e escrever no espaço do dono é livre; enviar, comentar, convidar ou apagar é 🔒.** Escrever inclui rascunho de e-mail, tarefa no ClickUp, documento no Drive, compromisso sem convidados e áudio do ElevenLabs. Um compromisso com convidados vira envio. | O critério é "alguém além do dono vê?". Rascunhos e tarefas são reversíveis e ficam só com ele; travar tudo tiraria a autonomia que o Avora precisa ter. |
| D19 | **ClickUp pelo token pessoal (`pk_`) e a API REST v2**, não pelo MCP oficial com OAuth previsto na Fase B. | O MCP remoto do ClickUp exige OAuth com cliente registrado e redirect público; o token pessoal dá acesso completo ao workspace do dono, sem servidor público, e a API REST é estável e testável. O cliente MCP genérico continua no plano para a cauda longa. |
| D21 | **Apps com servidor MCP oficial entram com um clique, como no Claude e no Codex.** O Avora descobre o login do servidor, se cadastra sozinho (registro dinâmico de cliente), abre o consentimento no navegador com PKCE e recebe o código numa porta `127.0.0.1` do app. Catálogo de 45 apps verificados um a um em 2026-11-11; qualquer outro servidor MCP entra pelo endereço. Substitui a parte de D19 que dizia que o MCP do ClickUp exigia cliente registrado e endereço público: o token do ClickUp fica só como plano B. | Era o jeito que o dono já conhecia, sem criar token nem app em painel de desenvolvedor. O registro dinâmico aceita o retorno local, então não precisa de porta pública (D10). |
| D20 | **Google por um cliente OAuth "App para computador" do próprio dono**, com PKCE e redirect em `127.0.0.1` capturado pelo app desktop. O refresh token fica só no cofre da VPS. | Funciona sem porta pública (D10) e sem verificação do Google, porque só o dono usa. |
| D22 | **Cada app aceita várias contas, e o funcionário escolhe pelo argumento `conta`.** A conexão ganhou um `id` próprio (a primeira conta de um app mantém o `kind` como id, então nada antigo mudou de lugar nem de chave no cofre). Com mais de uma conta usável, as ferramentas do app ganham `conta` com a lista; sem ele vale a principal. Cada conta tem a própria sessão MCP. | O dono usa várias contas do Google. Um argumento a mais em cada ferramenta custa menos contexto do que repetir as ferramentas por conta, e a primeira conta como padrão mantém o caso de uma conta só exatamente como era. |
| D23 | **Claude Code e Codex usam os Plugins pela ponte MCP do Avora**, com uma chave por execução, e não com credenciais próprias. Toda chamada passa pelo servidor, com as contas, o "Quem usa" e a aprovação do funcionário que delegou. | Mantém D18 e o cofre: nenhum token sai do servidor, e o CLI delegado não ganha mais poder que o funcionário. |
| D24 | **O modelo principal é escolhido em Configurações → Modelos**, entre provedores no formato OpenAI (NVIDIA, OpenRouter e afins, ou um llama-server local pela Tailscale). O do ambiente do servidor vira o provedor "NVIDIA do servidor", que vale até outro ser escolhido. Claude e Codex aparecem como assinaturas, nunca como modelo principal. | Trocar de cérebro sem reiniciar nem editar o servidor; a chave fica selada no cofre como a dos Plugins; llama.cpp direto (sem Ollama) porque o llama-server já fala OpenAI, com ferramentas pelo --jinja, e roda mais rápido. |
| D25 | **Projetos agrupam funcionários, como os projetos do Codex.** Cada projeto tem instruções (o `AGENTS.md` da pasta principal), uma pasta principal no PC ou na VPS e pastas extras. Um funcionário de projeto só vê os colegas do projeto e os universais; um universal (sem projeto) vê todos e trabalha em qualquer projeto. Claude Code e Codex delegados por um funcionário de projeto rodam na pasta do projeto, no nó onde ela fica. No PC, o runtime só aceita uma pasta que o dono escolheu no app daquele PC (`%APPDATA%\Avora\folders.json`). | Organizar por frente de trabalho sem misturar contexto, e dar a cada time a pasta e as regras dele. A lista de pastas liberadas fica no PC, fora do alcance do servidor: um servidor comprometido não faz o runtime trabalhar em qualquer pasta. |
| D26 | **Skills são saber escrito; ferramentas são programas do nó com ações fixas.** Uma skill segue o formato `SKILL.md` das Agent Skills (nome, descrição, passos) e fica no servidor, do time ou de um projeto. O prompt leva só nome e descrição; `skill_ler` carrega os passos quando o pedido casa. `skill_criar` pede aprovação do dono. Uma rotina pode seguir uma skill (workflow). Ferramentas (`yt-dlp`, `ffmpeg`, `pandoc`, ImageMagick, `tesseract`, `qpdf`, `whisper.cpp`) rodam pela ferramenta `ferramenta` em ações com argumentos fixos: o agente preenche valores, nunca flags; arquivos são caminhos relativos dentro da pasta da execução; sem shell (na VPS, dentro do bubblewrap); a saída nunca sobrescreve um arquivo. | Revelação progressiva deixa o contexto barato mesmo com muitas skills. O nó remonta o comando a partir do mesmo catálogo, então um servidor comprometido não consegue fazer o nó rodar outra coisa; e ações fixas dão ao modelo o que ele precisa (baixar, cortar, converter, OCR) sem o risco de um shell no PC do dono. |
| D27 | **Missões: o agente nativo é o dono; o Claude Code/Codex é a mão de cada rodada.** Uma missão guarda o objetivo, o checklist e o modelo da rodada (nó, conta, pasta, modo). Cada rodada é um job que ninguém espera, no mesmo nó, que continua a sessão da CLI. O fim de qualquer job passa por `missionJobEnded`, que acha a missão pelo `job_id` no banco e acorda o agente com o resultado numa mensagem `🎯 Missão` da conversa (com nova tentativa se a conversa estiver ocupada, e de novo no início do servidor). Limites: 8 rodadas por missão, 6 missões ativas e 120 min por rodada. `pode_editar` pede aprovação uma vez, no início. | O turno deixa de ficar preso até 30 min; o trabalho longo sobrevive a reinício porque o estado está no banco, não na memória; e o agente decide o próximo passo com o resultado na mão, em vez de a CLI virar o cérebro (regra das ferramentas). |
| D28 | **Execuções viram conversas à parte; a conversa longa é resumida, não cortada; rotinas podem disparar por evento.** Cada passo do Claude Code/Codex leva o `job` da execução, e o que a CLI diz vira passo `texto` (até 2000 caracteres), que fica fora dos passos do agente. O app mostra as execuções ativas aninhadas sob o agente e abre qualquer uma (ativa ou terminada) num painel próprio. O contexto é estimado (caracteres ÷ 3,6) por parte; a partir de 64 mil tokens as mensagens antigas viram um resumo em `conversation_summaries`, que entra no prompt de sistema, e as 12 mais recentes ficam inteiras. Gatilhos de rotina: conector (e-mail novo no Gmail, tarefa nova no ClickUp, conferidos a cada N min, com a primeira conferida só aprendendo o que já existe) e nó (PC ou VPS ligou/desligou). | O dono acompanha o que a ferramenta faz sem misturar com a conversa do agente; resumir mantém o fio de conversas de semanas sem estourar a janela nem pagar por mensagens velhas; e o evento só acorda a rotina, quem decide o que fazer continua sendo o agente (Fase C). |
| D29 | **O navegador dos agentes fica dentro do app, num painel ao lado da conversa (Chromium do QtWebEngine, perfil próprio); o app aberto é o nó `app`. O Chrome do PC por DevTools (chromedp) ficou opcional (`AVORA_BROWSER=1`).** O dono entra nos sites uma vez no painel e vê o agente navegar ali; o Avora nunca vê senhas e o agente não digita em campo de senha. O nó busca os comandos por long poll (`/v1/browser/app/next` no app, `/v1/runtime/browser/next` no runtime), sem job por ação. A página vira texto com elementos numerados; cliques e teclas são eventos de entrada reais. Clicar em enviar, publicar, comprar, pagar, apagar, seguir ou comentar, e enviar texto numa caixa de mensagem, pede aprovação (`navegador.enviar`). Cada ação traz um print para a visão ao vivo; o dono pode assumir o controle (os agentes esperam). Prints e imagens ficam em `files` e aparecem no chat como `![](avora:file/<id>)`. A pesquisa a fundo (`pesquisar`) é o Codex com busca ao vivo (`gpt-6.1-sol`, esforço alto), e DuckDuckGo, Yahoo e Bing ficam para `buscar_na_web`. | IP residencial e sessões reais do dono passam onde a VPS é bloqueada (Marketplace, Instagram, OLX); texto com números custa pouco contexto e funciona com qualquer modelo; a aprovação pelo rótulo do botão segura o que é irreversível sem travar a navegação. |
| D30 | **Objetivos com mandato: o dono dá um resultado que leva dias e um mandato (o que o agente pode fazer sozinho e o que nunca fazer); o agente persegue o objetivo numa conversa própria, com um funil de itens, estratégia e lições.** Ele decide quando acordar (`objetivo_atualizar acordar_*`, pelo que espera acontecer); o servidor acorda no horário ativo (8h–21h), faz uma revisão diária contra o prazo e relê sozinho as páginas vigiadas no navegador do app, acordando o agente só quando o texto mudou (números e espaços ignorados). Dentro do objetivo, uma ação travada que o mandato cobre passa por um fiscal (o modelo principal, resposta PERMITIDO/PERGUNTAR, dúvida = perguntar) e segue sem o dono; o resto pede aprovação, e uma recusa vira lição. | Rotina a cada 15 min e lista de tarefas não dão autonomia: o agente precisa de um resultado para perseguir, autoridade delimitada para agir sem pedir clique a clique, e despertar por evento ou expectativa. Vigiar por diferença custa quase nada; o fiscal separado segura o que sai do mandato. |
| D32 | **O WhatsApp do dono entra como aparelho conectado do servidor (whatsmeow, a biblioteca do whatsapp-mcp), dentro do avora-server, com as chaves no Postgres.** Agentes leem e mandam por ferramentas; enviar passa pela aprovação ou pelo mandato. "Mensagem para você" é o canal do dono com a Vega; resposta de um contato do funil acorda o objetivo. | Rodar o whatsapp-mcp (Go + Python + SQLite) no PC dependeria do PC ligado; a mesma biblioteca em Go roda 24h na VPS sem processo extra. O canal "para você" evita outro número. |
| D33 | **Mídia do WhatsApp sob demanda: a mensagem guarda o proto da mídia e o arquivo só é baixado quando o dono manda no próprio chat, quando um contato do funil manda, ou com `whatsapp_midia`; vira arquivo do chat (anexo, D31) e o áudio é transcrito pelo ElevenLabs Speech to Text da conta do dono.** | Baixar tudo que chega encheria o banco com fotos de grupo; o caminho dos anexos já entrega imagem ao Codex e texto de PDF. Transcrição pelo ElevenLabs porque ele já está conectado e é pago (não treina com o áudio); whisper no nó fica como alternativa local. | 2026-11-16 |
| D34 | **Instagram nativo em Go, no lugar de rodar o instagram-mcp (Python): com o token do login unificado da Meta (EAA..., graph.facebook.com, a conta do Instagram achada pelas Páginas do token ou dada como TOKEN#ID), que a Meta recomenda e segue atualizando; o token do login do Instagram (IG..., graph.instagram.com, renovado sozinho) também serve.** | Mesmo conjunto de ferramentas do mcpware/instagram-mcp, mas o token fica selado no servidor, os erros 190 viram "Reconectar" e publicar, responder e DM passam pela aprovação como o resto. O tipo do token decide o host, então o dono cola o que o painel gerar. | 2026-11-16 |
| D35 | **Marcar com @ no chat: o dono escolhe um app conectado, uma skill ou uma ferramenta e o turno diz ao agente para usar exatamente aquilo (as ferramentas do conector, os passos da skill já carregados).** | O agente às vezes ia pelo navegador ou adivinhava a skill; marcar é o jeito mais curto de o dono dizer "por aqui". Menção é texto na mensagem (`@Nome`), sem formato novo, e só vale para a mensagem em que aparece. | 2026-11-16 |
| D36 | **Tinder pela API privada do tinder.com (a do tinder-mcp-server), nativo em Go, com o token da sessão web do dono; curtir e mandar mensagem pedem aprovação, passar é livre.** | Não existe API oficial. | D37 | **Conectar pelo chat: o agente chama `pedir_conexao` e o passo vira um cartão na conversa (logo, Conectar, campo do token ou QR); ao conectar, o app avisa o agente na conversa.** | Chat-first: o dono não precisa sair da conversa para Plugins. O cartão é só um passo gravado (`pedir_conexao` + o tipo do app), sem formato novo de mensagem, e o estado vem de `/v1/connectors`, então um cartão antigo mostra "Conectado". | 2026-11-16 |
| D38 | **Esperar um evento (aguardar_evento) é uma espera do objetivo: o servidor roda a ferramenta de leitura do app (Gmail, ClickUp, DMs do Instagram, Tinder) a cada poucos minutos sem o modelo, aprende o que já existe na primeira vez e acorda o agente com o que chegou de novo, ou quando o prazo vence sem nada.** | Acordar de 3 em 3 horas para olhar a caixa gasta modelo e responde tarde. Em sequência, o turno não estoura a cota da assinatura de madrugada. | D44 | **Antigravity como terceiro executor (ferramenta `antigravity`), pelo CLI oficial `agy` em modo headless, só no PC.** O prompt entra como um evento stream-json e o stdin fecha; a resposta vem do evento `result`. Nunca `--dangerously-skip-permissions`. | D45 | **Compras pelas APIs oficiais com as chaves do dono, e o Apify nativo com várias contas em rodízio.** Mercado Livre: token de aplicativo (client credentials) no catálogo (`/products/search`, `/products/{id}/items`, mais vendidos), porque a busca pública de anúncios (`/sites/MLB/search`) passou a dar 403 para quase todo app. Shopee: Open API de afiliados (GraphQL assinado em SHA256).
